Technical Specification

Scroll Scrape

How Scroll Scrape is built: one Next.js app online on Vercel, with Supabase for sign-in and data, Gemini for reading and planning, and Google Maps for the facts.

Author: Krishna (solo) Devpost Learn · Build With AI: Basics 24 October 2026 Draft for review

How it works, in plain language

The screens

React pages in the browser: Home, Saved, Add, Plan, Profile, City View, Place Details and Memories.

The backend

Small server routes in the same Next.js project. They hold the secret keys, because anything in the browser can be seen by anyone.

Supabase: memory

Sign-in, the database of spaces and places, and photo files. Each user can only read their own rows.

Gemini: reasoning

Reads captions and screenshots, estimates busy times, and plans from your saves.

Google Maps: facts

Real address, hours, rating, price range, travel times, and the city map with pins.

The honesty rule: Gemini finds and chooses; Google Maps supplies the facts. The only AI guess is busy times, always labelled. The plan route also drops any place that isn't in your saves, so "only your saves" is enforced in code, not just requested.

Server routes

POST /api/identify · Gemini reads the post, Google finds the place
  1. Gemini returns { placeName, placeType, city, country, confidence, questions? }.
  2. Low confidence: ask for comments first, then return the flamingo's questions.
  3. Text Search "name, city" (IDs only, free) → Place Details (hours, rating, price range).
  4. Returns the confirmation card. If Google finds nothing, returns Gemini's fields so the place can still be saved.

Implements prd.md › Saving a Place

POST /api/lookup · look up again after you edit the card

Runs only the Google part with the edited name and city.

POST /api/places · estimate, then save
  1. Gemini: a one-line busy-times estimate, plus cost per person when Google has no price range.
  2. Create the city space if you said yes, otherwise use the existing one.
  3. Insert the place.

Implements prd.md › City Spaces

POST /api/plan · plan from saves only
  1. Work out the city; if none is named, the flamingo asks.
  2. Load your places in that city.
  3. Gemini picks stops by place ID from that list: { stops, notFound, followUp }.
  4. Guard: drop any ID that isn't yours.
  5. Google Route Matrix for travel times; check opening hours at each suggested time.
  6. Save to plans, then reply. With no stops at all: "Not found on your list."

Live

A Vercel URL, deployed from the public GitHub repo on every push to main.

Judges

Sign up instantly (no confirmation email), or use the demo account pre-filled with real Singapore places. Its details go in the submission and README.

Locally

npm install · copy .env.example to .env.local · npm run dev · open localhost:3000

Environment variables (never committed)
  • NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY: safe in the browser, because row-level security protects each user's data.
  • SUPABASE_SECRET_KEY: secret, used by the demo seed script only.
  • GEMINI_API_KEY: secret, server routes only.
  • GOOGLE_MAPS_SERVER_KEY: secret, Places and Routes only.
  • NEXT_PUBLIC_GOOGLE_MAPS_BROWSER_KEY: map only, locked to the site's web address.

Where it will break, and what you'll see

  • Gemini quota runs out: the flamingo asks for a short rest. Prevent it by checking the quota on day one and adding the $5 credit if needed.
  • Gemini can't identify the place: it asks for comments, then the flamingo asks questions.
  • Google can't find the place: "Not on Google Maps." The place can still be saved, and missing facts show "Not available".
  • Gemini suggests an unsaved place: the route drops it before you see it.
  • Photo has no location: it goes to an Unmatched list with a place picker.
  • Supabase pauses after a week idle: open the app every few days until judging ends on 30 October.

Decisions and open issues

Krishna decided

  • Next.js over React plus a Python backend, accepting the learning curve.
  • Online on Vercel, because a laptop-only app won't cut it for judging.
  • Login and an online database instead of browser storage. This updated the PRD.
  • Supabase over Appwrite and PocketBase, after checking the free limits.
  • The four-sheet schema; sign-in with email and username, nothing more.
  • Gemini for its free tier; Google Maps billing within the free allowance.

The learning question

"Is Supabase's free tier enough?" Text is tiny, and photos are the real limit. Shrinking them to about 250 KB raises capacity from about 300 to about 4,000. Also from this step: why a backend exists, which is that secret keys can't live in the browser.
